## D1 交互范式：桌面 Tab

- **决策**：整个应用是 SPA，路由只剩 `__root` + `index`。每个 SSH 连接打开一个仿 OS 桌面 Tab，桌面内通过图标、窗口、任务栏完成所有操作。
- **理由**：这是项目差异化核心定位（"远程 Linux 桌面外壳"）；UI 设计已确定该范式，"多页面路由"（terminal/files/monitor/ai 各自页面）与它冲突，统一时以桌面 Tab 为准。
- **影响**：路由不承载功能页面；窗口管理是纯客户端状态；SFn 就近平级放在消费它的桌面应用目录（`apps/<app>/<app>.functions.ts`）。

## D2 通信范式：零 Hono、零 WebSocket

- **决策**：通信全部由 TanStack Start 承载——业务 RPC 用 `createServerFn`（SFn），流式/下载/health 用 Server Route `server.handlers` 返回 `Response(ReadableStream)`。不引入 Hono、不使用 WebSocket、不引入 CSRF 中间件。
- **理由**（fsdx-web 实证）：
  1. fsdx-web 中 Hono 仅挂在 Nitro server entry 上注册 `/health`，**一行业务都没承载**，业务与流式全靠 SFn + Server Route——"Hono 作为 API 网关"是早期设想
  2. `/health` 用 Server Route 一行即可实现，Hono 连挂载点角色都不需要
  3. Electron 本地回环无**远程**跨站攻击面，CSRF 保护在远程场景无必要；但**本机进程与浏览器恶意本地页面**可访问回环服务，鉴权必要性见 D19（以 request 中间件统一 token 校验覆盖，等效 CSRF 且挡本机进程）
  4. SFn 返回值经 `startSerializer` 序列化，**async generator / 裸 ReadableStream 无法流式返回**（源码验证，W0 结论）；流式正解是 Server Route。**（D21 后修正）**：官方在 start-server-core 引入 RawStream 帧协议后，SFn 支持流式返回（handler 返回 `ReadableStream` 或 async generator，客户端逐块/for-await 消费，技术验证记录实测通过），流式接口两种范式皆可，迁移与否按场景取舍
- **影响**：文档/代码中禁止出现 Hono、WebSocket、`@xterm/addon-attach`；统一用 `@tanstack/react-start`。review 级审批也走 SFn 体系（`approvalSFn` + server 内存挂起表），不引入独立通信通道。**D19 起**不再单独引入 CSRF 中间件（`serverFn` 端点由全局鉴权的自定义头 `X-SSHOS-TOKEN` 预检等效覆盖，且能挡非浏览器本机进程）。**流式**：SFn 支持（ReadableStream / async generator，见技术验证记录）与 Server Route 并存，按场景取舍。

## D3 Policy 命名：safe / review / block

- **决策**：命令分类三级命名为 `safe` / `review` / `block`，全链路一致：Policy Engine 判定 → UI 状态色（绿/黄/红）→ 数据库 `log.classification` 枚举。
- **理由**：早期 schema 曾用 `caution/dangerous`，与 `safe/review/block` 两套命名冲突；统一为三分级模型。
- **影响**：`log.classification` 枚举值 = `safe | review | block`。

## D4 认证枚举

- **决策**：`authType` = `password` / `privateKey` / `systemKey` / `agent`。
- **理由**：覆盖全部认证场景（含 electerm 同款系统密钥扫描与 ssh-agent）；早期表单"密码 / 密钥文件 / 代理"缺少系统密钥、多了不存在的"代理"选项。
- **影响**：新建/编辑连接表单的认证方式下拉 = 密码 / 私钥（粘贴）/ 系统密钥 / SSH Agent。

## D5 历史模型

- **决策**：`connection_history` 表每次连接插一行（含 `duration`），侧栏"历史"页 UI 按连接去重、更新访问时间、按使用频率排序展示（上限 50 条）。
- **理由**：表记每次连接保留审计价值（时长），UI 聚合满足"最近连接"体验，两边兼容。
- **影响**：写入发生在连接断开时（记录本次时长）；查询由 UI 层聚合。

## D6 应用范围

- **决策**：MVP 桌面应用为 Terminal / Files / Monitor / AI（均含 `window` surface）+ Clock（`statusbar` surface，自启）。Monitor 额外贡献 `panel` surface（桌面状态卡片）。
- **理由**：Editor（文本编辑）、Network（网络配置）不在 MVP 范围，剔除避免范围蔓延；后续可作为 app 扩展。Clock 作为 statusbar 形态的最小示例，验证 App 框架的多 surface 与自启能力。
- **影响**：桌面应用目录 `src/apps/` 保留 terminal / files / monitor / ai / clock 五个应用；桌面图标只出现 window surface 的四个。

## D7 AI 引擎

- **决策**：AI 引擎 = `@earendil-works/pi-coding-agent`（SDK 模式），不是自研 AI 层。
- **理由**：npm 验证存在（`exports['.']` 提供 types + import 可编程入口）；已集成 15+ provider；session 树可白送审计日志。`@pi.dev/sdk` 经查**不存在**，严禁使用。
- **影响**：`pi-agent.ts` 中 `import { Pi } from '@earendil-works/pi-coding-agent'`；具体 `Pi` 类 API（`stream`/`registerTool`）以实际版本为准，见待验证清单。

> **API 更新（v0.84.2 核实）**：Pi SDK 已重构，`Pi` 类 / `registerTool` / `stream()` 均不存在。SDK 模式入口为 `createAgentSession({ model, customTools, noTools, sessionManager })` → `{ session }`，流式经 `session.onEvent()` 事件流，自定义工具用 `defineTool`。docs/02 §8 的 pi-agent.ts 代码示例过时，实现时以新 API 为准。

## D8 数据存储

- **决策**：`node:sqlite`（Node 22.5+ 内置，DatabaseSync）+ drizzle-orm；敏感凭据（密码/私钥/passphrase）经 Electron `safeStorage` 加密后入库。
- **理由**：零原生依赖、嵌入式单文件，与 Electron 桌面定位匹配；对齐 fsdx 的 db-sqlite skill（事务回调必须同步等陷阱）。
- **影响**：迁移走 drizzle-kit generate + bootstrap 程序化 migrate；`log` 表含 `result` 字段（执行结果）；WebDAV 整库同步仅推送主 db 文件（推送前 WAL checkpoint），个人云同步为既定路线（MVP 后交付）。

## D9 AI 对话流

- **决策**：AI 对话流底层 SSE 由 Server Route 或 SFn handler 返回 `Response` 提供，客户端消费流式文本。
- **理由**：SFn 原生序列化不支持流，需 SSE Response 或 Server Route 承载。
- **实现注记（W3 定稿 → D21 修订）**：SFn 返回 `Response` 被 `startSerializer` 序列化层吞掉（实测 200 空 body），AI 对话曾走 Server Route `/api/ai/chat`（SSE）；D21 后官方 RawStream 帧协议使 SFn 支持流式，改 `aiChatSFn` 返回 `ReadableStream<AiTextDelta>`（typed stream），客户端逐块消费（`@tanstack/ai-react` 的 `useChat` **未采用**，依赖保留），见技术验证记录「SFn 流式返回实测」「流式接口迁移 SFn」。

## D10 客户端状态管理

- **决策**：客户端状态按三层管理——服务端数据（连接/分组/设置）用 TanStack Query 缓存；桌面 UI 状态（Tab 列表、窗口管理器、焦点、主题）用 Zustand；流式数据（PTY 输出、监控指标、AI 对话）不进全局 store，由组件内局部 hook（`use-metrics-stream` / TerminalWindow / AiPanel 内联流消费）直接消费。
- **理由**：Query 与 TanStack 生态一致，`queryKey` 天然映射 SFn 请求，连接增删改后失效刷新；窗口状态是桌面全局态，Zustand 轻量且 selector 按需订阅避免整树重渲染；流式数据高频更新，放全局 store 会造成无谓抖动。
- **影响**：`src/stores/` 放置窗口/Tab store；连接列表等数据走 `useQuery` 消费 SFn；流式 hook 保持组件局部。

## D11 Tab 边界：一连接一 Tab

- **决策**：一个连接 = 一个 Tab，一一对应。连接已打开时重复点击（侧栏连接项、历史项、`ssh://` Deep Link）只切换聚焦到已有 Tab，不新建；需要"同一台机器独立多开"时通过连接项右键「复制连接」生成指向同一主机的新配置。
- **理由**：保持 OS 隐喻"一台机器 = 一个桌面"的一致性；Tab 生命周期 = 连接生命周期，`sessionId`、断线重连、审计日志保持单一来源；桌面内多窗口（multi-channel）已覆盖多终端多开需求。
- **影响**：连接点击是"打开或聚焦"的幂等操作；跨 Tab 共享连接不再存在。

## D12 App 插件框架

- **决策**：桌面应用即插件。每个 app 以插件包形式注册，manifest 声明三要素——**多 surface**（`window` / `panel` / `statusbar`，一个 app 可同时贡献多种，如 monitor 的完整窗口 + 桌面状态面板）、**能力**（`pty` / `sftp` / `exec` / `ai` / `metrics`，框架据此裁剪 ctx 暴露面）、**放置槽位**。生命周期裁剪为四个钩子：`onCreate(ctx)` / `onRestore(state)` / `onSave()` / `onShutdown(reason)`。会话状态与布局快照存 `connection_setting`（key = `app.<id>.state` / `desktop.layout`），app 偏好存全局 `setting`。
- **理由**：借鉴 VS Code 扩展（声明式 manifest + 贡献点）、Android Activity（实例终止 + SavedState 恢复）、KDE Plasmoid（同一控件多放置形态）；"Tab 关闭 = 实例销毁、状态保留，下次进入自动还原"贴近真实 OS 的会话恢复体验；能力声明为未来第三方 app 隔离打基础。
- **影响**：新增 `app-framework/`（types / registry / app-manager / dispatcher）与每个 app 的 `app.ts`；布局快照与 app 状态恢复成为 App 框架的固有能力；`onShutdown(reason)` 让 app 感知自己是被系统退出、Tab 关闭还是手动关闭。
- **实现注记（W1-W3 后校准）**：`AppManager` 为**纯客户端**实现（settings / audit / log 经 SFn 网关注入，不直连服务端模块），由 `app-instances.ts` 按连接维护单例；渲染层（图标 / 面板 / 状态栏）由 registry 的 surface 查询驱动，窗口内容按 app id 分发，`AppManager` 仅负责实例生命周期与状态持久化；五内置 app 在 `apps/index.ts` 一次性注册。

## D13 UI 方案：Tailwind CSS v4 + shadcn/ui（明暗双主题）

- **决策**：UI 层采用 Tailwind CSS v4 + shadcn/ui；主题走 shadcn CSS 变量 token，按 `:root`（light）/ `.dark`（dark）双值声明，切换通过根元素 `.dark` class 完成。MVP 只支持 **light / dark 两档**（默认 dark，GitHub Dark 基底），但 token 结构预留多主题扩展（新增主题 = 追加一组 token 值，不做任意色盘定制）。UI 主题偏好全局持久化到 `setting` 表（key = `appearance.theme`）。
- **理由**：v4 CSS-first 零配置、构建期扫描，与 Vite/TanStack Start 无缝；shadcn 是 headless Radix + 可控 token 的组件底座，GitHub 配色（界面设计 §1.2）可直接映射为 token，避免手写组件样式；明暗双档覆盖绝大多数桌面场景，多主题由 token 机制免费支撑、成本极低。
- **影响**：`globals.css` 集中声明全部 token（明暗各一套）；项目语义色变量（`--bg` / `--accent` 等）映射 shadcn token，UI 层只消费后者；表单、表格、日期、Excel 工具库（@tanstack/react-form / react-table / dayjs / hucre）与之配套；终端配色（ANSI）独立于 UI 主题，二者可任意组合。

## D14 国际化：i18next

- **决策**：国际化采用 `i18next`，默认语言 `zh-CN`，UI 文案全部走 i18n 资源文件集中管理，不散落在组件内。
- **理由**：开源项目面向多语言用户；i18next 生态成熟（React 绑定、插值、复数、回退链），Electron 场景可与运行时 locale 联动。
- **影响**：文案定义在 `locales/` 资源目录（zh-CN 为首个完整语言包）；后续新增语言只需补翻译资源，不改组件逻辑。

## D15 右键菜单框架：App 贡献点

- **决策**：App 插件可通过**贡献点**为远程文件 / 文件夹注册右键菜单项——manifest 声明静态结构（`contributes.contextMenus`：`{ id, target, label, icon, group, order, when }`），`setup(ctx)` 里 `ctx.menus.registerHandler(id, handler)` 绑定命令式处理器（对齐 VS Code `contributes.contextMenus` 模式）。文件管理窗口右键时聚合本 Tab 运行中 app 的贡献项，内置项在前、app 项以分隔线隔开。
- **理由**：文件管理器是本项目核心且特殊场景，需要向 app 生态开放右键能力（如"上传到对象存储""在 xx 中打开"），否则每个功能都改 files 内置菜单会失控；声明式 + 命令式分离让菜单结构可静态审查、处理器可复用；`target` 维度（file/folder）为未来终端选择、桌面图标等目标预留。
- **影响**：AppManifest 新增 `contributes.contextMenus`，AppContext 新增 `menus.registerHandler`；仅声明 `sftp` 能力的 app 可注册文件/文件夹菜单；处理器动作走 SFn，写操作过 Policy Engine；注册返回 Disposable，随 app 启停回收。

## D16 文件管理器设计：参考 Win/Mac

- **决策**：文件管理器交互借鉴 Windows Explorer 与 macOS Finder 的成熟范式——工具栏（后退/前进、路径栏、新建、上传、视图、排序、刷新）+ 面包屑/直接输入路径双模式 + 状态栏 + 快捷键体系；**MVP 只做详细列表 + 图标两档视图**，拖拽语义按目标判定（上传/下载/移动·复制选择），文件预览（Quick Look/预览窗格）、列视图、画廊、收藏夹列为后续迭代。
- **理由**：用户对文件管理的操作心智高度依赖主流 OS 习惯，直接复用可降低学习成本；两档视图覆盖 99% 场景，预览等需 SFTP 下载大文件体验差，不值得占 MVP。
- **影响**：界面设计 §6 全章按此改写；视图切换、列管理、拖拽语义、快捷键表、右键菜单结构（内置分组 + 应用贡献分组）落文档；后续迭代能力在 §6.9 显式标注。

## D17 写操作策略覆盖范围

- **决策**：策略引擎覆盖**全部写操作类 SFn**，两类分类入口并存：命令执行（`execCommandSFn`，shell 文本规则）与 SFTP 变更写操作（`sftpDeleteSFn` / `sftpRenameSFn`（SFTP rename 原语覆盖重命名与移动），路径规则，敏感路径 block、其余 review）。低风险新建（`sftpMkdirSFn`、文件上传 Route）分类 safe 直接放行；`sendInputSFn`（终端逐键流）不挂策略——逐键分段无法可靠分类。
- **理由**：架构原则"读路径直通，写路径过策略引擎"（docs/02 §2）要求**渲染层与 AI 的写操作走同一道护栏**，若只覆盖命令执行，则文件删除/移动（含右键菜单、AI 文件工具）存在无策略路径，违背"无绕过路径"承诺；文件写操作用路径规则而非命令正则，与命令分类解耦、规则可独立演进。
- **影响**：`packages/policy` 新增 `classifyFileOperation` 与路径规则集；中间件以工厂形式提供 `command` / `file` 两种 kind；`sftpDeleteSFn` / `sftpRenameSFn` 挂 `sftpPolicyMiddleware`；审计中间件按 SFn 覆盖范围统一包裹；"写操作无绕过路径"承诺在命令与文件两类写操作上均成立。

## D18 凭据加密接线：safeStorage 保护 master key 的密钥桥接

> **已被 D21 取代**：web 服务独立运行后不再依赖 Electron safeStorage / env 注入，主密钥改由 setup 生成的数据目录 `master.key` 文件（0600）承载，桌面壳与独立模式同构。本决策保留历史记录。

- **决策**：凭据加密采用**密钥桥接**——Electron main 进程用 `safeStorage` 生成并加密持久化随机 master key（`userData/master.key`），启动 Nitro 子进程时经环境变量 `SSHOS_MASTER_KEY` 注入；子进程 `db/crypto.ts` 用其派生 AES-256-GCM 密钥加解密凭据。`setCredentialEncryptor` 保留为未来 headless 服务模式（进程内启动 Nitro）的注入点，当前无调用点。
- **理由**：Nitro server 是 Electron main **spawn 的独立子进程**（无 Electron API），无法直接调用 `safeStorage`。两个候选方案中：进程内启动 Nitro 会让 main 进程承担 HTTP server 职责，偏离「外壳不承载业务」且与未来 headless 服务模式冲突；密钥桥接改动最小、保持 main 外壳角色与 web 包纯 Node 身份，且 safeStorage 加密落盘的 key 不随应用打包、天然隔离。
- **影响**：新增 `packages/desktop/src/secure-key.ts`（`getOrCreateMasterKey`）；main 生产启动注入 `SSHOS_MASTER_KEY` + `NODE_ENV=production`（此前未注入 NODE_ENV，生产降级告警不触发）；safeStorage 不可用（如 Linux 无 keyring）时降级公开密钥并双侧告警；master key 已存在但解密/写入失败时 fail-fast（启动即退出，不静默降级，避免存量凭据不可解密且新凭据等价明文）；dev 模式保持降级明文（本地无真实凭据）。

## D19 全局请求鉴权：TanStack request 中间件统一 token 校验

> **已被 D21 取代**：鉴权 token 不再由 main 经 env 注入，改为「启动密码登录签发 JWT」；中间件形态与豁免面（SFn 一律校验、`/api/*` 除 health 校验、页面/静态资源/health 豁免）保留。本决策保留历史记录与威胁模型（仍适用：挡本机进程与浏览器恶意本地页面）。

- **决策**：在 `start.ts` 的 `requestMiddleware` 挂全局鉴权中间件（`middleware/auth.ts`），对所有 **SFn 调用**与 **`/api/*` Server Route** 校验 `X-SSHOS-TOKEN`（与 Electron main 注入的 `SSHOS_AUTH_TOKEN` 比对），**页面 / 静态资源 / `/api/health` 豁免**。token 由 main 生成：经 env 注入 web server 子进程、经 `additionalArguments` + preload 注入渲染层 `window.sshOS.authToken`；SFn 客户端请求经 `serverFns.fetch` 统一带头，手动 fetch 端点（pty / metrics / ai.chat / sftp / deeplink）经 `lib/api-fetch.ts` 统一带头。
- **理由**：D2 原判「Electron 本地回环无浏览器跨站攻击面」只覆盖了**远程跨站**，漏掉**本机进程**与**浏览器恶意本地页面**——任何本机程序可直接 HTTP 调用回环服务的 SFn（含 `execCommandSFn` 等写操作）；TanStack 官方默认要求 serverFn 端点受保护（内置 `defaultCsrfMiddleware`，本项目此前用 `requestMiddleware: []` 禁用它并触发告警）。token 方案同时挡两类本机攻击者：浏览器跨源页面读不到渲染层 window 的 token、且带自定义头触发 CORS 预检被拒；普通本地进程猜不到 16 字节随机 token。能读 main 进程 env/内存的进程级木马属防护天花板之外（本就可直接改数据库文件）。
- **影响**：`middleware/auth.ts`（`isProtected` 豁免逻辑 + 单测）；`main.ts` 生成 `SSHOS_AUTH_TOKEN` + `additionalArguments`；`preload.ts` 暴露 `authToken`；`start.ts` 挂 `requestMiddleware` + `serverFns.fetch`；`lib/api-fetch.ts` 统一注入；**无 `SSHOS_AUTH_TOKEN` env（纯浏览器 `dev:web`）时不启用校验**；deeplink 路由不再单独校验（全局已覆盖）。

## D20 发行版适配：三层适配模型

- **决策**：对不同 Linux 发行版 / 镜像做三层适配：
  1. **发行版 Profile（core）**：连接后经 `/etc/os-release` → `/etc/redhat-release` → `/etc/debian_version` → `lsb_release` → `uname` 回退链探测，产出 `{ id, family, packageManager, initSystem, coreutils }`，按会话缓存（`clearDistroProfile` 随断开清理）
  2. **App 远程能力探测**：`AppManifest.remoteRequirements` 声明远程工具依赖；`probeToolsSFn` 用固定只读命令 `command -v` 批量探测（工具名白名单字符集校验，不接受用户任意文本），按会话缓存 TTL 60s；UI 按结果 gate / hint / fallback
  3. **缺失依赖安装引导**：必需工具缺失自动渲染 `InstallGuide`，增强工具缺失显示「安装」入口。三路径：**一键安装**（知识库 `install-knowledge.ts` 按包管理器生成命令 → `execWithPolicy` → 包管理器写操作命中 review → 审批重放，无绕过路径）、**手动安装**（展示可复制命令 / 源码步骤）、**AI 对话式安装**（预填 prompt 唤起 AI 面板，AI 工具同样过策略）
- **理由**：软件/进程/Docker 等未来 app 是发行版差异重灾区；指标采集已直读 `/proc`（天然发行版无关）；策略规则若穷举包管理器会漏（如 Alpine 的 `apk`、openSUSE 的 `zypper`），须由 Profile 语义化。
- **影响**：`packages/core/src/distro-profile.ts`；`packages/web/src/services/capabilities/`（schemas/server/functions/probe/install-knowledge）；`AppManifest.remoteRequirements`；`components/InstallGuide.tsx` / `AppCapabilities.tsx`；策略包管理器规则加词边界并补全 `apk|zypper|emerge|snap|flatpak`；`command -v` 入只读白名单（精确 `command -v` 形态，防借壳）；`exec.service` 从 `apps/ai` 上移至 `services/ssh`（AI 工具 / execCommandSFn / 安装引导共用）。

## D21 web 服务模式：独立启动 + JWT 登录认证 + 桌面壳

- **决策**：web 包作为独立服务直接启动（`node .output/server/index.mjs`），不依赖 Electron。认证改为**启动密码登录签发 JWT**（HS256，Node 内置 crypto，零依赖）；Electron 桌面端退化为**纯浏览器壳**（spawn web server + health 自检 + 加载窗口），废除 main 注入 env 的 `SSHOS_AUTH_TOKEN`（D19）与 `SSHOS_MASTER_KEY` 密钥桥接（D18），深链为壳自己的本地职责（冷启动经 URL 参数传给渲染层，运行时仅聚焦窗口）。
- **server.json**（数据目录，0600）：`{ "passwordHash", "serverSecret", "port": 3000, "bind": "127.0.0.1" }`。密码仅存 scrypt 哈希（`salt:hash`）；`serverSecret` 为 JWT 签名密钥（setup 随机生成）；`port`/`bind` 手工编辑后重启生效，**默认仅本机**，`bind: "0.0.0.0"` 显式开启局域网访问（未配 TLS 时启动打印明文告警）。
- **首次启动（未配置模式）**：`server.json` 无 `passwordHash` 时服务仅放行**公开 SFn**（`lib/public-sfns` 注册表，认证 setup/login/status 与 bootstrap 状态）、`/api/health`、页面与静态资源，业务请求一律 401。前端 `AuthGate` 调 `authStatusSFn` 分流：未配置 → `SetupWizard`（`setupSFn` 设密码，同时生成 serverSecret 与 `master.key`，返回 token 自动登录）；未登录 → `LoginForm`（`loginSFn`）；已登录 → 桌面。
- **token**：JWT 默认 30 天过期，无刷新（过期重新登录）；登出 = 客户端丢弃 token（无状态，服务端无吊销）；客户端存 localStorage（桌面壳与浏览器同构）。
- **主密钥**：凭据加密改由数据目录 `master.key`（32 字节随机 hex，0600）承载，setup 时生成；`crypto.ts` 回退链 = `setCredentialEncryptor`（预留）→ `master.key` → dev-only（仅非生产）；生产缺 master.key fail-fast，不降级明文。主密钥独立于启动密码，改密码不触发凭据重加密。
- **理由**：桌面壳不承载业务，web 服务是唯一事实来源，纯 web 模式与桌面模式完全同构；JWT 无状态、重启不失效、天然多客户端；默认仅本机监听修正了此前 Nitro 未设 HOST 默认绑定所有接口的暴露；安全最小化（scrypt 哈希 + JWT 是仅有的两道基线，不做过期刷新/吊销/防抢占等加料）。
- **影响**：新增 `services/auth/`（config/password/jwt + auth.schemas/server/functions）、`lib/public-sfns.ts`（公开 SFn 注册表，规避 SFn 内容哈希无法按前缀识别）、`lib/auth-client.ts`、`components/AuthGate/SetupWizard/LoginForm/BootstrapGate`；认证接口为**公开 SFn**（`setupSFn`/`loginSFn`/`authStatusSFn`/`bootstrapStatusSFn`，定义处注册，server.ts 入口强制 import 确保集合就绪），`middleware/auth.ts`（`lib/http-guard.ts`）对未注册 SFn 一律校验、`/api/health` 豁免；`server.ts` 顶部按 server.json 设置 `NITRO_HOST/PORT`（默认 127.0.0.1）；`routes/api/deeplink.tsx` 删除；desktop 删除 preload / secure-key / token 注入 / `/api/deeplink` HTTP 推送；D18/D19 机制废止（中间件形态与豁免面保留）。

## D24 UI 与前端组件重构（shadcn + token 全量化）

- **架构调整**：新增 `components/ui/`（shadcn 底座 27 组件）、`components/shell/`（Sidebar/TabBar/Desktop/Taskbar/Window）、`components/shared/`（AppIcon/StatusDot/CommandCard 等）、`theme/`；**`app-framework/app-views.tsx`** 视图注册表（app 注册自身 windowView/panelView/statusbarView），替代 Desktop/Taskbar 硬编码 `WINDOW_CONTENT`/`PANEL_CONTENT`/`STATUSBAR_CONTENT`/`ICON_COLOR` 分发表；`lib/utils.ts`（cn）+ `lib/format.ts`（收敛跨 app 重复的字节/速率/使用率/时间格式化）。
- **AI 命令卡片（docs §8.3/8.4 落地）**：服务端 `execCommand` 工具透出 `tool-call` 流帧（命令 + 策略分类 safe/review/block + 结果），客户端 `shared/CommandCard.tsx` 渲染三态卡片（左描边 + 状态标签 + 截断输出）；**不改审批架构**（review 仍经 ApprovalDialog 弹窗，命令卡片为展示增强）。
- **理由**：原前端无 shadcn 落地、样式内联 `var()` 与 tailwind/硬编码三套并存、图标 emoji/Unicode/首字母混杂、动画与交互反馈缺失、token 残缺且深浅硬编码混用；D13 的 shadcn 承诺未兑现，本次一次性落地。技术选型用户指定：图标 Remix、图表 TanStack 新库、动画用成熟库。
- **影响**：`packages/web` 依赖新增 `@remixicon/react`/`motion`/`sonner`/`@tanstack/charts`/`clsx`/`tailwind-merge`/`tw-animate-css`/`@fontsource-variable/*`/`class-variance-authority`/`radix-ui`；`biome.json` 启用 `css.tailwindDirectives`（解析 `@theme`）；`globals.css` 全量 token + `@theme inline` 语义类映射；旧语义别名（`--bg`/`--bg2`/`--bg3`/`--ink`/`--muted`/`--rule`/`--accent`/`--accent2`/`--warn`/`--ok`/`--ok-bg`）在 P4 **重定义为语义 token 的引用**（消除双值漂移）；auth/审批/设置等主要组件已迁移语义类，`ConnectionDrawer`/`ModelSettingsPanel`/`ProviderDrawer`/`InstallGuide`/`AppCapabilities` 的组件级样式迁移为后续增量（别名已单源化，功能不受影响）。UI 开发规范见 `docs/07-UI范式与规则.md`。
