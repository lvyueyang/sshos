## D1 交互范式：桌面 Tab

- **决策**：整个应用是 SPA，路由只剩 `__root` + `index`。每个 SSH 连接打开一个仿 OS 桌面 Tab，桌面内通过图标、窗口、任务栏完成所有操作。
- **理由**：这是项目差异化核心定位（"远程 Linux 桌面外壳"）；UI 设计已确定该范式，"多页面路由"（terminal/files/monitor/ai 各自页面）与它冲突，统一时以桌面 Tab 为准。
- **影响**：路由不承载功能页面；窗口管理是纯客户端状态；SFn 就近平级放在消费它的桌面应用目录（`apps/<app>/<app>.functions.ts`）。

## D2 通信范式：零 Hono、零 WebSocket

- **决策**：通信全部由 TanStack Start 承载——业务 RPC 用 `createServerFn`（SFn），流式/下载/health 用 Server Route `server.handlers` 返回 `Response(ReadableStream)`。不引入 Hono、不使用 WebSocket、不引入 CSRF 中间件。
- **理由**（fsdx-web 实证）：
  1. fsdx-web 中 Hono 仅挂在 Nitro server entry 上注册 `/health`，**一行业务都没承载**，业务与流式全靠 SFn + Server Route——"Hono 作为 API 网关"是早期设想
  2. `/health` 用 Server Route 一行即可实现，Hono 连挂载点角色都不需要
  3. Electron 本地回环无浏览器跨站攻击面，CSRF 保护无必要
  4. SFn 返回值经 `startSerializer` 序列化，**async generator / 裸 ReadableStream 无法流式返回**（源码验证）；流式正解是 Server Route
- **影响**：文档/代码中禁止出现 Hono、WebSocket、`@xterm/addon-attach`、SFn async generator 流式；统一用 `@tanstack/react-start`。review 级审批也走 SFn 体系（`approvalSFn` + server 内存挂起表），不引入独立通信通道。

## D3 Policy 命名：safe / review / block

- **决策**：命令分类三级命名为 `safe` / `review` / `block`，全链路一致：Policy Engine 判定 → UI 状态色（绿/黄/红）→ 数据库 `log.classification` 枚举。
- **理由**：早期 schema 曾用 `caution/dangerous`，与 `safe/review/block` 两套命名冲突；统一为三分级模型。
- **影响**：`log.classification` 枚举值 = `safe | review | block`。

## D4 认证枚举

- **决策**：`authType` = `password` / `privateKey` / `systemKey` / `agent`。
- **理由**：覆盖全部认证场景（含 electerm 同款系统密钥扫描与 ssh-agent）；早期表单"密码 / 密钥文件 / 代理"缺少系统密钥、多了不存在的"代理"选项。
- **影响**：新建/编辑连接表单的认证方式下拉 = 密码 / 私钥（粘贴）/ 系统密钥 / SSH Agent。

## D5 历史模型

- **决策**：`connection_history` 表每次连接插一行（含 `duration`），侧栏"历史"页 UI 按连接去重、更新访问时间、按使用频率排序展示（上限 50 条）。
- **理由**：表记每次连接保留审计价值（时长），UI 聚合满足"最近连接"体验，两边兼容。
- **影响**：写入发生在连接断开时（记录本次时长）；查询由 UI 层聚合。

## D6 应用范围

- **决策**：MVP 桌面应用为 Terminal / Files / Monitor / AI（均含 `window` surface）+ Clock（`statusbar` surface，自启）。Monitor 额外贡献 `panel` surface（桌面状态卡片）。
- **理由**：Editor（文本编辑）、Network（网络配置）不在 MVP 范围，剔除避免范围蔓延；后续可作为 app 扩展。Clock 作为 statusbar 形态的最小示例，验证 App 框架的多 surface 与自启能力。
- **影响**：桌面应用目录 `src/apps/` 保留 terminal / files / monitor / ai / clock 五个应用；桌面图标只出现 window surface 的四个。

## D7 AI 引擎

- **决策**：AI 引擎 = `@earendil-works/pi-coding-agent`（SDK 模式），不是自研 AI 层。
- **理由**：npm 验证存在（`exports['.']` 提供 types + import 可编程入口）；已集成 15+ provider；session 树可白送审计日志。`@pi.dev/sdk` 经查**不存在**，严禁使用。
- **影响**：`pi-agent.ts` 中 `import { Pi } from '@earendil-works/pi-coding-agent'`；具体 `Pi` 类 API（`stream`/`registerTool`）以实际版本为准，见待验证清单。

## D8 数据存储

- **决策**：`node:sqlite`（Node 22.5+ 内置，DatabaseSync）+ drizzle-orm；敏感凭据（密码/私钥/passphrase）经 Electron `safeStorage` 加密后入库。
- **理由**：零原生依赖、嵌入式单文件，与 Electron 桌面定位匹配；对齐 fsdx 的 db-sqlite skill（事务回调必须同步等陷阱）。
- **影响**：迁移走 drizzle-kit generate + bootstrap 程序化 migrate；`log` 表含 `result` 字段（执行结果）；WebDAV 整库同步仅推送主 db 文件（推送前 WAL checkpoint），个人云同步为既定路线（MVP 后交付）。

## D9 AI 对话流

- **决策**：AI 对话流由 `@tanstack/ai-react` 的 `useChat` 消费；底层 SSE 由 Server Route 或 SFn handler 返回 `Response` 提供。
- **理由**：`@tanstack/ai-react` 存在且支持 streaming chat；SFn 原生序列化不支持流，需 SSE Response 或 Server Route 承载。
- **待验证**：`stream()` / connection adapter 的实际 API 签名（TanStack AI 已演进为 adapter 体系）；定稿后回填技术架构 §8。

## D10 客户端状态管理

- **决策**：客户端状态按三层管理——服务端数据（连接/分组/设置）用 TanStack Query 缓存；桌面 UI 状态（Tab 列表、窗口管理器、焦点、主题）用 Zustand；流式数据（PTY 输出、监控指标、AI 对话）不进全局 store，由组件内局部 hook（`use-pty-stream` / `useChat`）直接消费。
- **理由**：Query 与 TanStack 生态一致，`queryKey` 天然映射 SFn 请求，连接增删改后失效刷新；窗口状态是桌面全局态，Zustand 轻量且 selector 按需订阅避免整树重渲染；流式数据高频更新，放全局 store 会造成无谓抖动。
- **影响**：`src/stores/` 放置窗口/Tab store；连接列表等数据走 `useQuery` 消费 SFn；流式 hook 保持组件局部。

## D11 Tab 边界：一连接一 Tab

- **决策**：一个连接 = 一个 Tab，一一对应。连接已打开时重复点击（侧栏连接项、历史项、`ssh://` Deep Link）只切换聚焦到已有 Tab，不新建；需要"同一台机器独立多开"时通过连接项右键「复制连接」生成指向同一主机的新配置。
- **理由**：保持 OS 隐喻"一台机器 = 一个桌面"的一致性；Tab 生命周期 = 连接生命周期，`sessionId`、断线重连、审计日志保持单一来源；桌面内多窗口（multi-channel）已覆盖多终端多开需求。
- **影响**：连接点击是"打开或聚焦"的幂等操作；跨 Tab 共享连接不再存在。

## D12 App 插件框架

- **决策**：桌面应用即插件。每个 app 以插件包形式注册，manifest 声明三要素——**多 surface**（`window` / `panel` / `statusbar`，一个 app 可同时贡献多种，如 monitor 的完整窗口 + 桌面状态面板）、**能力**（`pty` / `sftp` / `exec` / `ai` / `metrics`，框架据此裁剪 ctx 暴露面）、**放置槽位**。生命周期裁剪为四个钩子：`onCreate(ctx)` / `onRestore(state)` / `onSave()` / `onShutdown(reason)`。会话状态与布局快照存 `connection_setting`（key = `app.<id>.state` / `desktop.layout`），app 偏好存全局 `setting`。
- **理由**：借鉴 VS Code 扩展（声明式 manifest + 贡献点）、Android Activity（实例终止 + SavedState 恢复）、KDE Plasmoid（同一控件多放置形态）；"Tab 关闭 = 实例销毁、状态保留，下次进入自动还原"贴近真实 OS 的会话恢复体验；能力声明为未来第三方 app 隔离打基础。
- **影响**：新增 `app-framework/`（types / registry / app-manager / dispatcher）与每个 app 的 `app.ts`；布局快照与 app 状态恢复成为 App 框架的固有能力；`onShutdown(reason)` 让 app 感知自己是被系统退出、Tab 关闭还是手动关闭。

## D13 UI 方案：Tailwind CSS v4 + shadcn/ui（明暗双主题）

- **决策**：UI 层采用 Tailwind CSS v4 + shadcn/ui；主题走 shadcn CSS 变量 token，按 `:root`（light）/ `.dark`（dark）双值声明，切换通过根元素 `.dark` class 完成。MVP 只支持 **light / dark 两档**（默认 dark，GitHub Dark 基底），但 token 结构预留多主题扩展（新增主题 = 追加一组 token 值，不做任意色盘定制）。UI 主题偏好全局持久化到 `setting` 表（key = `appearance.theme`）。
- **理由**：v4 CSS-first 零配置、构建期扫描，与 Vite/TanStack Start 无缝；shadcn 是 headless Radix + 可控 token 的组件底座，GitHub 配色（界面设计 §1.2）可直接映射为 token，避免手写组件样式；明暗双档覆盖绝大多数桌面场景，多主题由 token 机制免费支撑、成本极低。
- **影响**：`globals.css` 集中声明全部 token（明暗各一套）；项目语义色变量（`--bg` / `--accent` 等）映射 shadcn token，UI 层只消费后者；表单、表格、日期、Excel 工具库（@tanstack/react-form / react-table / dayjs / hucre）与之配套；终端配色（ANSI）独立于 UI 主题，二者可任意组合。

## D14 国际化：i18next

- **决策**：国际化采用 `i18next`，默认语言 `zh-CN`，UI 文案全部走 i18n 资源文件集中管理，不散落在组件内。
- **理由**：开源项目面向多语言用户；i18next 生态成熟（React 绑定、插值、复数、回退链），Electron 场景可与运行时 locale 联动。
- **影响**：文案定义在 `locales/` 资源目录（zh-CN 为首个完整语言包）；后续新增语言只需补翻译资源，不改组件逻辑。

## D15 右键菜单框架：App 贡献点

- **决策**：App 插件可通过**贡献点**为远程文件 / 文件夹注册右键菜单项——manifest 声明静态结构（`contributes.contextMenus`：`{ id, target, label, icon, group, order, when }`），`setup(ctx)` 里 `ctx.menus.registerHandler(id, handler)` 绑定命令式处理器（对齐 VS Code `contributes.contextMenus` 模式）。文件管理窗口右键时聚合本 Tab 运行中 app 的贡献项，内置项在前、app 项以分隔线隔开。
- **理由**：文件管理器是本项目核心且特殊场景，需要向 app 生态开放右键能力（如"上传到对象存储""在 xx 中打开"），否则每个功能都改 files 内置菜单会失控；声明式 + 命令式分离让菜单结构可静态审查、处理器可复用；`target` 维度（file/folder）为未来终端选择、桌面图标等目标预留。
- **影响**：AppManifest 新增 `contributes.contextMenus`，AppContext 新增 `menus.registerHandler`；仅声明 `sftp` 能力的 app 可注册文件/文件夹菜单；处理器动作走 SFn，写操作过 Policy Engine；注册返回 Disposable，随 app 启停回收。

## D16 文件管理器设计：参考 Win/Mac

- **决策**：文件管理器交互借鉴 Windows Explorer 与 macOS Finder 的成熟范式——工具栏（后退/前进、路径栏、新建、上传、视图、排序、刷新）+ 面包屑/直接输入路径双模式 + 状态栏 + 快捷键体系；**MVP 只做详细列表 + 图标两档视图**，拖拽语义按目标判定（上传/下载/移动·复制选择），文件预览（Quick Look/预览窗格）、列视图、画廊、收藏夹列为后续迭代。
- **理由**：用户对文件管理的操作心智高度依赖主流 OS 习惯，直接复用可降低学习成本；两档视图覆盖 99% 场景，预览等需 SFTP 下载大文件体验差，不值得占 MVP。
- **影响**：界面设计 §6 全章按此改写；视图切换、列管理、拖拽语义、快捷键表、右键菜单结构（内置分组 + 应用贡献分组）落文档；后续迭代能力在 §6.9 显式标注。

## D17 写操作策略覆盖范围

- **决策**：策略引擎覆盖**全部写操作类 SFn**，两类分类入口并存：命令执行（`execCommandSFn`，shell 文本规则）与 SFTP 变更写操作（`sftpDeleteSFn` / `sftpRenameSFn`（SFTP rename 原语覆盖重命名与移动），路径规则，敏感路径 block、其余 review）。低风险新建（`sftpMkdirSFn`、文件上传 Route）分类 safe 直接放行；`sendInputSFn`（终端逐键流）不挂策略——逐键分段无法可靠分类。
- **理由**：架构原则"读路径直通，写路径过策略引擎"（docs/02 §2）要求**渲染层与 AI 的写操作走同一道护栏**，若只覆盖命令执行，则文件删除/移动（含右键菜单、AI 文件工具）存在无策略路径，违背"无绕过路径"承诺；文件写操作用路径规则而非命令正则，与命令分类解耦、规则可独立演进。
- **影响**：`packages/policy` 新增 `classifyFileOperation` 与路径规则集；中间件以工厂形式提供 `command` / `file` 两种 kind；`sftpDeleteSFn` / `sftpRenameSFn` 挂 `sftpPolicyMiddleware`；审计中间件按 SFn 覆盖范围统一包裹；"写操作无绕过路径"承诺在命令与文件两类写操作上均成立。
